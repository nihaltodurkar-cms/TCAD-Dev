     M18 — Small-Signal AC Analysis (Phase 1: Device1D)

     Context

     ARCHITECTURE.md names M18 as the explicit next milestone on the spine
     (M13 -> M15 -> M17 -> M18 -> M21 -> M23 -> M27), unblocked now that M17
     (transient) has landed and been re-verified. Scope per the roadmap:
     "frequency-domain perturbation of the converged DC point (complex linear
     solve with the same analytic Jacobian); Y-parameters, C-V(f), admittance
     for any two-terminal; junction and MOS capacitances from the AC solve."
     Depends only on M17, which is done.

     This session already closed the M16 gate-verification gap (found and
     fixed three test-only sign/threshold bugs, pytcad/M16-BTBT-PLAN.md).
     M18 is the next concrete, unblocked milestone the user asked to pursue.

     Every prior milestone (M15/M16/M17) drives Device1D from outside
     device.py through its already-frozen _residual_jacobian(psi, n, p, bc) -> 
     (F, J, Jn, Jp), never modifying device.py itself. M18 follows
     the same amendment-free pattern M17 established: a new sibling module
     built entirely as post-processing/perturbation around the existing DC
     Jacobian, no new Models flag (confirmed: M17 added none either — AC
     is a different equation formulation, not a physics term to toggle).

     Scoped to Phase 1: Device1D (1D) only, mirroring M17's own phasing
     (1D core first, 2D/GUI as later, separately-gated phases). 2D
     (Device2D) AC and GUI wiring are explicitly out of scope this pass —
     named as the natural Phase 2/3 continuation, same as M17-TRANSIENT-PLAN.md
     does for its own phases.

     Design

     New file: pytcad/pytcad/ac.py (mirrors pytcad/pytcad/transient.py's
     shape exactly).

     The physics

     At a converged DC operating point (psi0, n0, p0) (device.solve_bias/
     solve_equilibrium already called — same precondition as
     solve_transient, checked the same way: raise if device.psi is None),
     device._residual_jacobian(psi0, n0, p0, bc0) returns F0 ≈ 0 and the
     real DC Jacobian J0. Linearizing a small harmonic perturbation
     u(t) = u0 + δu·exp(jωt) around this point, the interior continuity
     rows' time-derivative term (dV·dn/dt, -dV·dp/dt — the same physical
     term transient.py's backward-Euler discretizes as
     ∓dVi/dt_s·(n-n_old)) becomes ∓dVi·jω_s·δn/δp in the frequency domain
     (d/dt -> jω for a harmonic signal; ω_s = ω·t0, t0 = device.Ns/device.R0,
     the exact same time-scale transient._time_scale uses). This gives:

     J_ac(ω) = J0 + 1j*omega_s * Cmat

     where Cmat has exactly the structure of transient._step_residual_jacobian's
     storage-term addition with dt_s = 1.0 substituted in (extra_vals = [-dVi, 
     +dVi] at [idx_n, idx_p], same idx_n = 3*arange(1,N-1)+1 /
     idx_p = 3*arange(1,N-1)+2 convention). Do not import this from
     transient.py (it's a private, tightly-coupled helper bundled with
     Newton/backtracking logic that doesn't factor out cleanly) — recompute
     the ~5-line matrix directly in ac.py. Gate the two independently as
     numerically identical (see Gates, G-CONSISTENCY) instead of sharing code,
     matching the project's existing convention of small, independently-gated
     per-milestone modules (M15/M16 don't share code with each other either).

     The forcing: driving contact drive ("left" or "right") with a unit AC
     voltage, the other contact AC-grounded (held at its DC value) — the
     standard one-port small-signal measurement. Because the Poisson row at
     each contact is a pure Dirichlet identity row in J0 (∂F/∂psi[node] = 1,
     confirmed in exploration: device.py lines ~1466-1556), the forcing
     vector is trivial: b = zeros(3N, dtype=complex); b[3*driven_node] = 1.0.
     Solve δu = spsolve(J_ac.tocsc(), b) — a single linear complex solve,
     no Newton loop (this is genuinely linear in δu at fixed (psi0,n0,p0)).

     Terminal-current sensitivity: Jn[edge]/Jp[edge] (edge 0 for the left
     contact, edge N-2 for the right) depend only on the 6 DOFs of the two
     adjacent nodes. Compute a real sensitivity row vector S via central
     finite difference on the exact same Jn, Jp arrays _residual_jacobian
     already returns (reusing the exact code path transient._record_current
     already reuses, not re-deriving Scharfetter-Gummel by hand — avoids
     mishandling degeneracy/FD-statistics/etc. terms already baked into
     _residual_jacobian). Only 6 scalar directions perturbed (psi/n/p at the
     two edge-adjacent nodes) — cheap, ~12 extra _residual_jacobian calls
     per frequency point.

     I_ac = S · δu                      (complex, scaled units)
     Y(ω) = I_ac / 1.0                  (unit excitation -> Y directly)
     Y_phys [S/cm^2] = Y_scaled * device.J0 / device.VT
     C(ω) = Im(Y_phys) / (2*pi*f)       [F/cm^2]
     G(ω) = Re(Y_phys)                  [S/cm^2]

     Public interface (pytcad/pytcad/ac.py)

     class ACResult:
         def __init__(self, freqs, Y, C, G):
             self.freqs = ...   # [Hz]
             self.Y = ...        # complex [S/cm^2]
             self.C = ...         # [F/cm^2]
             self.G = ...         # [S/cm^2]

     def ac_sweep(device, freqs, drive="left") -> ACResult:
         """Small-signal admittance Y(f) of a two-terminal Device1D at its
         CURRENT converged DC operating point (call solve_equilibrium/
         solve_bias first — same precondition as solve_transient).
         freqs: array of frequencies [Hz] (not angular). drive: which
         contact carries the 1V AC excitation; the other is AC-grounded.
         Raises TypeError for anything other than Device1D (2D/3D AC is out
         of scope this phase, refused explicitly rather than silently wrong
         -- same convention as M16's G-F / M21's 3D+gates refusal)."""

     Gates (pytcad/tests/test_m18_ac.py)

     Follow the project's standing rule: gate against something independent,
     report measured numbers honestly rather than tune thresholds to pass
     (the lesson from this session's M16 fix).

     1. G-CONSISTENCY: ac.py's Cmat construction is numerically
        identical to transient._step_residual_jacobian's storage-term
        addition evaluated with dt_s=1.0 (import the private helper in the
        TEST only, not in ac.py itself) — a strong regression check against
        the already-FD-gated M17 formula, standing in for a fresh FD-Jacobian
        derivation (justified in the plan comment above: the affine map
        u -> J0·u + jω·Cmat·u trivially reproduces Cmat under an FD probe,
        so an independent-formula equivalence check is the more informative
        gate here).
     2. G-LOWF (the ARCHITECTURE-mandated low-f-limit gate): at f -> 0,
        ac_sweep's Re(Y) matches a finite-difference dI/dV computed via
        two independent nearby solve_bias calls (existing, already-validated
        path — same idea as current_density()); C(f->0) matches a
        finite-difference dQ/dV computed via the same
        Q * sum((n-p)*dx) formula TransientResult.stored_charge already
        uses, evaluated at two nearby bias points via solve_bias. This
        single gate independently validates BOTH Cmat and the sensitivity
        vector S at once (measure and report the actual relative error, not
        an assumed tolerance).
     3. G-JUNCTION-C: at equilibrium (V=0) on the same abrupt p+/n+ (or
        moderate) diode used elsewhere in the suite, ac_sweep's low-f C
        is compared against a freshly-derived (no existing pin in the repo,
        confirmed via exploration) analytic abrupt-junction depletion
        capacitance C_j = eps / W, W = sqrt(2*eps*Vbi/Q * (1/Na + 1/Nd))
        (same Vbi/W formula test_validation.py::test_built_in_potential
        already uses and gates independently) — report the measured relative
        error rather than assume a tight tolerance, since Device1D's finite
        structure (not the formula's infinite one-sided assumption) will
        introduce some real discrepancy.
     4. G-ROLLOFF (the literature/honest-limits-aware version of
        ARCHITECTURE's "3dB roll-off... against the analytic stored-charge
        pole from M17"): M17's own plan doc (section 5) explicitly found
        Qs ~= I_F*tau_p sign-ambiguous and off by a factor of several, and
        deferred it — so this gate does NOT assume a clean tau_p pole
        exists to match against. Instead: sweep several decades of frequency

     M20 (M12-S3) — Coupled-Newton Density-Gradient Reformulation

     Context

     M20-DENSITY-GRADIENT-PLAN.md (the folded M12-S3 density-gradient
     quantum correction) is PARTIALLY GREEN, left open by explicit prior
     user decision. The current MOSCapacitor.solve_psi(dg=True) and
     Device1D.solve_equilibrium(dg=True) both LAG the quantum potential
     Lambda_n/Lambda_p outside the Newton loop (Gummel-style outer
     fixed point: solve classical Poisson with Lambda frozen, recompute
     Lambda from the converged psi, repeat). A prior hard-debug session
     fixed a real convergence bug in that loop, but once it converges
     cleanly it converges to the WRONG physics: a gamma sweep from 0.001 to
     3.0 found NO value that reproduces the literature/Schrodinger-Poisson
     centroid band (~2-8 nm) — below ~0.01 the DG effect is negligible,
     above ~0.03 it jumps straight to a numerical-clamp-saturated ~0.02-0.3
     nm regime, with no intermediate physical solution. Boundary-condition,
     mesh-resolution, and units/formula hypotheses were all tested and
     ruled out (see plan section 6). The diagnosis: this is a documented
     failure mode of LAGGING a quantum potential outside the Newton loop —
     production TCAD tools solve it COUPLED into the same Newton system.
     The three open gates are test_gc_dg_centroid_within_factor2_of_sp,
     test_gc_classical_centroid_is_the_sub_debye_tail,
     test_gd_dg_changes_the_physics_in_every_required_direction, all in
     tests/test_m20_dg.py and all exercising MOSCapacitor(dg=True)
     specifically (confirmed by reading the test file — no equivalent
     centroid gate exists for Device1D(dg=True)).

     The user explicitly chose this path (coupled-Newton reformulation)
     over "try a literature gamma anyway" (which the plan doc's own
     diagnosis already shows won't work — the gamma sweep covered the full
     plausible range) or leaving it open.

     Design

     Replace the lagged outer fixed point with a genuinely coupled Newton
     system: add Lambda_n[i], Lambda_p[i] as PER-NODE UNKNOWNS solved
     SIMULTANEOUSLY with psi[i] in one Newton iteration (3 unknowns/node,
     interleaved [psi, Lambda_n, Lambda_p] per node — mirrors
     device.py's own [psi, n, p] interleaving convention for the full
     DD Newton system).

     Equations (per node i)

     Poisson row (unchanged shape, but n, p now COUPLED not lagged):
     n_i = nie_s * exp(psi_i) * exp(-Lambda_n_i / VT)
     p_i = nie_s * exp(-psi_i) * exp(-Lambda_p_i / VT)
     same flux-divergence residual moscap.py's solve_psi already
     builds, just with n, p depending on Lambda_n_i, Lambda_p_i as
     live Newton unknowns instead of a lagged array.

     Lambda_n row — the residual form of dg.py's own defining
     equation (quantum_potential's docstring formula), so the coupled
     solve reduces to the EXACT SAME algebraic relationship the already-
     gated quantum_potential/G-B Airy/G-C S-P-reference code uses, not a
     new formula:
     Lambda_n_i * g_i + pref_n_i * dd_i = 0      (interior nodes)
     Lambda_n_i = 0                               (boundary nodes, i=0,N-1)
     where g_i = sqrt(n_i), dd_i is the exact 3-point non-uniform
     second-difference quantum_potential already computes (mirror that
     formula verbatim, evaluated on the PHYSICAL mesh self.x in cm — NOT
     the scaled self.xs the Poisson rows use — matching
     quantum_potential's own convention exactly, since solve_psi
     currently calls quantum_potential(self.x, ...) with physical x),
     and pref_n_i = gamma * HBAR^2 / (2 * m_n* * M0 * Q) * 1e4 (same SI
     prefactor quantum_potential uses, so pref need not be re-derived —
     call a small refactored helper, see below).

     Lambda_p row: identical structure with p, m_p_star.

     Jacobian (derive once, reuse for both g_i dependencies)

     g_i = sqrt(n_i) depends on psi_i and Lambda_n_i at the SAME
     node only (dg_i/dpsi_i = g_i/2, dg_i/dLambda_n_i = -g_i/(2*VT),
     from dn_i/dpsi_i = n_i, dn_i/dLambda_n_i = -n_i/VT). Since dd_i
     is a linear combination of g_{i-1}, g_i, g_{i+1}, the Lambda_n row's
     nonzero Jacobian columns are exactly {psi_{i-1}, Lambda_n_{i-1}, psi_i, 
     Lambda_n_i, psi_{i+1}, Lambda_n_{i+1}} — a 6-wide stencil per
     interior row (chain rule through dd_i's three g terms, each
     differentiated by the two-variable rule above). The Poisson row gains
     two new same-node columns, dF_psi_i/dLambda_n_i = dV_i * n_i / VT
     and dF_psi_i/dLambda_p_i = -dV_i * p_i / VT wait sign check against
     existing residual convention rho = n - p - C
     (dF/dLambda_n_i = -dV_i * d(rho_i)/dLambda_n_i = -dV_i * (dn_i/dLambda_n_i)
     = -dV_i*(-n_i/VT) = dV_i*n_i/VT; symmetric for
     Lambda_p_i with the opposite p sign) — write out and hand-verify
     every entry directly against _step_residual_jacobian-style code
     before committing, then let the FD-Jacobian gate (mandatory, see
     Gates) be the actual proof, not the hand derivation.

     Assemble as one (3N, 3N) sparse CSR matrix per Newton iterate (COO
     triplets, same add(r, c, v) accumulation style device.py's
     _residual_jacobian already uses), spsolve via
     linsolve.solve_linear (the same call solve_psi already makes) —
     no new linear-algebra machinery.

     Robustness

     Damped Newton with d = np.clip(d, -3.0, 3.0) on psi (existing
     convention) and an ANALOGOUS clip on Lambda_n/Lambda_p steps
     (magnitude bound in units of VT, e.g. +-10*VT per step — tighter
     than the existing LAMBDA_MAX_VT=20 hard clamp on the VALUE, since
     this bounds the STEP not the final value). If a single full-gamma
     Newton solve from Lambda=0 initial guess does not converge reliably
     (to be measured, not assumed), add gamma continuation: ramp gamma from
     a small value up to the target in a strength ladder (same pattern
     solve_bias's M15/M16 stiff-generation continuation and
     continuation.py already use), warm-restarting (psi, Lambda_n, Lambda_p)
     between ramp steps. Implement the plain coupled Newton
     first and only add continuation if it's actually needed — measure
     before adding complexity.

     M19 — Self-Heating (Phase 1: steady-state, 1D)

     Context

     ARCHITECTURE.md lists M19 as [L] (large), the next unstarted
     milestone on the roadmap. Scope per the spec: "lattice-temperature
     equation coupled to DD (Joule term + divergence of heat flux), thermal
     BCs (isothermal, thermal resistance to ambient); optional Seebeck
     term. 1D first, then 2D." Acceptance: Joule heating of a uniform
     resistor vs analytic T(x) parabola; electrothermal feedback in a diode
     I-V vs published self-heating roll-off; thermal-off bit-identity;
     FD-Jacobian gate on the coupled block system. Stated dependency: M17
     (transient machinery), which is done.

     Exploration finding that reshapes the plan: Device1D's entire
     nondimensionalization (self.VT, self.Ns, self.LD, self.J0,
     self.mu_n0/mu_p0, self.nie, self.tau_n/tau_p, ...) is built
     ONCE at __init__ from a single SCALAR T, and used as fixed arrays
     throughout every subsequent Newton solve. Making T a genuine,
     spatially-varying, monolithically-coupled 4th Newton unknown (psi, n,
     p, T per node) would require rearchitecting that entire scaling
     framework — a much larger undertaking than any milestone this session
     has attempted, and disproportionate to what the acceptance gates
     actually require. It also does not match how production TCAD tools
     usually offer self-heating either: a common, well-established mode is
     "isothermal DD + outer thermal loop" (Gummel-style between the
     electrical and thermal equations), which is what this plan uses —
     not a shortcut around a known-bad pattern (unlike M20's DG lagging,
     which had a documented specific defect), but a standard, previously-
     proven architecture here for a different physical reason (T enters
     almost every scaled quantity, not just one term).

     Also found: no thermal conductivity property exists anywhere in
     materials.py today — contradicts the milestone spec's "no new
     material work" note. A kappa_th300 constant + kappa_th(T) power-law
     method (mirroring the existing Eg(T)/Nc(T)/Nv(T) pattern) is a
     small, necessary, and honestly-flagged addition.

     Design

     1. New material property (small addition, pytcad/pytcad/materials.py)

     Add to Semiconductor: kappa_th300: float (thermal conductivity at
     300K, W/(cm·K); silicon ≈ 1.48 W/(cm·K)) and a method kappa_th(T)
     using the standard empirical power law kappa_th300 * (T/300)**-1.33
     (Sze & Ng; the well-established Si thermal-conductivity temperature
     dependence). Mirrors the existing Eg/Nc/Nv T-dependence pattern
     exactly — same file, same style, published constant.

     2. New module pytcad/pytcad/thermal.py — standalone steady-state heat 
     solver

     Mirrors transient.py/ac.py's established pattern: a new sibling
     module, device.py untouched. Solves, on a 1D mesh (physical cm, can
     reuse device.x or an independent mesh),

     -d/dx( kappa_th(T) dT/dx ) = H(x)      [W/cm^3]

     with H(x) a caller-supplied heat-source density and either
     isothermal (T = T_ambient at a boundary) or thermal-resistance
     (Robin: -kappa_th dT/dx = (T_boundary - T_ambient)/R_th_area, R_th_area
     in K·cm²/W) boundary conditions per side. Because kappa_th(T) is
     itself T-dependent, this is a genuinely nonlinear 1D BVP — a real,
     self-contained Newton solve (own residual/Jacobian, own FD-Jacobian
     gate, satisfying the "FD-Jacobian gate on the coupled block system"
     acceptance criterion without needing a 4-unknown monolithic system).
     kappa_th constant-in-T is the special case that reduces to a single
     linear tridiagonal solve — useful for the closed-form gate below.

     class ThermalBC:                  # "isothermal" or "resistance"
         ...

     def solve_lattice_temperature(x, H, material, T_ambient,
                                    bc_left, bc_right,
                                    opts=None) -> np.ndarray[T]

     Gate 1 (uniform resistor vs analytic parabola): a uniform,
     constant H and CONSTANT kappa_th (an explicit, honestly-labeled
     special case — the closed-form check needs kappa fixed to compare
     against a clean parabola) on a bare 1D rod with isothermal ends at
     T_ambient has the exact solution T(x) = T_ambient + H/(2*kappa) * x*(L-x).
     Compare directly — no Device1D involvement needed at all
     for this gate, a fully independent unit test of thermal.py.

     3. Joule heating from a converged Device1D solve

     H(x) for the electrothermal case comes from the device's own,
     already-computed, edge-based fields: `H_edge = (device.Jn + device.Jp)
     - device.E_field()[W/cm^3] (current density × field, the standard DD-level 
       Joule term; no recombination/generation or Peltier/Seebeck heat — those 
       are explicitly out of scope, see Honest Limits), box- integrated onto 
       nodes with the samedV-style half-box convention device.py's own Poisson 
       assembly already uses. A small helper in thermal.py, 
       joule_heating_density(device), computes this — reusing 
       device.Jn/device.Jp/device.E_field()/device.h`, not re-deriving
       the SG current.

     4. Electrothermal (two-way) coupling: 
     pytcad/pytcad/thermal.py::solve_electrothermal

     def solve_electrothermal(build_device, bias, T_ambient, bc_left, bc_right,
                               material, max_outer=30, tol=1e-3, opts=None)

     build_device(T) is a caller-supplied factory (e.g. lambda T: Device1D(x, 
     dop, T=T, models=...)) — the Gummel loop's own device
     reconstruction, matching Device1D's existing scalar-T constructor
     exactly, no new constructor argument needed. Outer loop: build the
     device at the current candidate temperature, solve_equilibrium() +
     solve_bias(bias) (existing, unmodified calls), compute H(x) via
     joule_heating_density, solve solve_lattice_temperature for T(x),
     take a representative device temperature (peak T(x), the physically
     relevant one for mobility/roll-off) as the next candidate, repeat
     until the candidate temperature converges. Returns the final device,
     T(x) profile, and outer-iteration history.

     Gate 2 (electrothermal I-V roll-off): sweep bias on a diode with
     solve_electrothermal, compare against an isothermal iv_sweep at
     the same bias — self-heating must show the qualitatively-expected
     signature (current below the isothermal curve at high bias / high
     dissipation, i.e. negative feedback from mobility degradation, not
     runaway) — the same "measure and report the qualitative signature

     M21 Phase 3d — Device2D(unstructured=True) Integration

     Context

     M21 Phase 3 (general unstructured 2D FV assembly) is fully built and
     gated as STANDALONE modules: pytcad/gmsh_mesh.py,
     pytcad/region_resolver.py, pytcad/unstructured_assembly.py,
     pytcad/unstructured_poisson.py, pytcad/unstructured_dd.py — all
     already FD-Jacobian gated, golden-parity gated against the structured
     Device2D solver, and exercised end-to-end in
     tests/test_m21_phase3.py's diode_bias_solve fixture. The one
     explicitly-named remaining piece (per M21-PHASE3-MESHING-PLAN.md) is
     wiring these into Device2D itself so a user gets the SAME public API
     (solve_equilibrium(), solve_bias(voltages), terminal_current(name))
     on an unstructured mesh as on a structured one — "a thin wrapper, not
     new physics."

     Key finding from exploring Device2D.__init__: it is deeply
     structured-mesh-specific — (Ny, Nx) reshaping, dVx/dVy outer
     product, et_x/et_y directional edge arrays, Caughey-Thomas doping-
     dependent mobility, heterostructure material lists, FD statistics,
     incomplete ionization. NONE of this applies to an unstructured
     triangle mesh. unstructured_dd.py's own docstring is explicit that
     it is homojunction-only: uniform mu_n_max/mu_p_max (no
     Caughey-Thomas), no heterojunction ln(nie) edge term, tau_n0/
     tau_p0 constants (no Scharfetter doping-dependent lifetime). So the
     wrapper cannot "just reuse the same constructor with a flag" — it must
     branch to a genuinely separate code path early, and REFUSE any
     Models() flag or config the unstructured physics core doesn't
     support, exactly the "refuse rather than silently drop" convention
     Device2D.__init__ already uses for impact/btbt/dg/
     incomplete_ion/field_mobility.

     Design

     Constructor signature (additive, unstructured=False default)

     Device2D(mesh, doping, ..., unstructured=False)

     When unstructured=True: mesh must be a GmshMesh
     (pytcad.gmsh_mesh.GmshMesh), and doping must be a dict {region_name: 
     doping_value [cm^-3]} (the natural per-region
     adaptation of the structured doping array argument, since there is
     no (Ny, Nx) grid to reshape a per-node array into — this mirrors
     evaluate_doping_at_nodes's existing doping_by_region parameter
     exactly, not a new convention).
